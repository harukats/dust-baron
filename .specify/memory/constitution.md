# Dust Baron プロジェクト憲章

## 基本原則

### I. 日本語による仕様と意思決定

以降に作成・更新する仕様書、計画書、タスク、レビュー結果、説明文は、すべて日本語で
記述しなければならない。技術判断の理由、検証結果、制約、未解決事項、PR の説明も
この規則に従う。コード識別子、ファイルパス、コマンド、API 名、原文の引用は、
正確性のため元の表記を維持してよい。その意味や判断への影響は日本語で説明する。
この規則だけを理由に、既存のゲーム内表示や識別子を翻訳してはならない。

仕様ではプレイヤーが得る結果と受け入れ条件を定義し、計画では実現方法と選定理由を、
タスクでは作業と完了条件を記述する。共通の言語と用語により、仕様からレビューまで
判断の根拠を追跡できる状態を維持する。

### II. 純粋なゲームコアと保守可能なコード

`src/config.ts`、`src/economy.ts`、`src/storage.ts` は Phaser を import せず、
モジュール読み込み時に DOM やブラウザ専用 API に依存してはならない。
調整値は `config.ts`、ゲームルールは `economy.ts` の `State` に対する純粋関数、
永続化の副作用は `storage.ts`、表示・入力・演出は Phaser 側に配置する。
ルールや調整値をシーンや UI に重複実装してはならない。

TypeScript の厳格な型検査と明示的な `.ts` import を維持し、Node の型除去で
実行できない enum、namespace、コンストラクターのパラメータープロパティを使用しない。
Biome の整形・静的解析規則に従い、既存の責務と部品を再利用する。
新しい依存や抽象化は、解決する具体的な問題と保守負担を計画に記録する。
この分離により、ブラウザなしでゲームルールを検証でき、表示変更の影響を限定できる。

### III. 振る舞いとリスクに基づく検証

ゲームルール、購入計算、生産量、マイルストーン、セーブ解析、オフライン収益を
変更するときは、受け入れ条件に対応する `node:test` を追加または更新する。
正常系に加え、変更に関係する境界値、不正入力、回帰条件を検証する。
不具合修正では、修正前に問題を再現する検証を行い、修正後に同じ条件で解消を確認する。
テストは実装の構造ではなく、入力に対する結果と保持すべき不変条件を確認する。

表示、入力、音声、シーン遷移、再起動を変更するときは、ブラウザまたは対象 WebView
で該当する操作を検証し、環境・手順・結果を日本語で記録する。
低リスクの文言・装飾変更には、内容確認や画面確認に応じた検証を選び、
意味のない自動テストを増やさない。
マージ前に必須 CI の `lint` と `test` を通過させ、型検査やテストを無効化して
不具合を隠してはならない。未実施・失敗した検証は、理由と影響を明記する。

### IV. 一貫したユーザー体験と進行状態の保護

ライブ状態は `storage.ts` の `run.state` に保持し、シーン遷移と再起動を通じて
同じランを継続する。セーブ読み込みとオフライン収益の加算は、`run.state` が
未初期化の場合にのみ行い、重複加算してはならない。
セーブ形式の変更は既存データへの影響を評価し、互換性を維持するか移行方法を定義する。
保存領域が利用できない場合もゲームを継続可能にし、不正なセーブの解析で停止させない。

UI は既存の Graphics と Text、`ui.ts`、`ShopRow.ts` の構成を基準とし、
同じ操作には同じ表記・購入条件・反応を提供する。マウスと対応するキーボード操作の
結果を一致させ、購入可否と数量をプレイヤーが判別できる表示にする。
固定 1280×720 と `Scale.FIT` を維持し、縮小表示で主要な操作部が欠けないことを確認する。
ピクセルアートは対象テクスチャの NEAREST フィルタリングを維持し、
文字と粒子の滑らかさを損なうグローバル設定変更を避ける。

効果音は Phaser の音声出力に接続し、ミュートとマスター音量を反映する。
BGM の重複再生を防ぐ。ブラウザ版とデスクトップ版でゲームルールと主要操作を共有する。
これらの規則は、進行の喪失や二重計算を防ぎ、操作への信頼を維持するために適用する。

### V. 測定可能な性能とライフサイクル管理

毎フレーム呼ばれる処理では、表示に変化がない場合の再描画、不要なオブジェクト生成、
同期ストレージアクセスを追加してはならない。`ShopRow.set()` は表示の差分を確認して
必要な場合だけ再描画する。保存は既存の定期保存・購入時保存を基準にする。

描画、粒子、更新ループ、アセット量、保存頻度に影響する機能の計画では、
実装前に測定環境、負荷条件、測定時間、指標と数値による合格基準を定義する。
通常プレイでは 60 FPS を目標とし、フレーム時間・入力応答・メモリ・読み込み時間から
変更に適した指標を選ぶ。目標は実測済みの保証とは区別する。
同じ条件で変更前後を比較し、合格基準を超える退行は解消するか、
根拠を記録した例外としてレビューで承認を受ける。測定なしに高速化を断定しない。

再利用されるシーンの一時状態は `create()` で明示的に初期化し、
Phaser.Scene の組み込みプロパティ名を独自フィールドで上書きしない。
追加したイベント購読、タイマー、音声、ゲームオブジェクトは適切な終了時に解除・破棄し、
再起動を繰り返しても重複処理や継続的なメモリ増加を起こさないことを検証する。

## 技術・配布上の制約

- 基盤は Phaser 4、Vite、TypeScript、pnpm、Tauri 2 とする。
  pnpm は `package.json` の `packageManager` に従い、依存変更では対応するロックファイルを更新する。
- Phaser の API はインストール済みバージョンの関連スキル・資料で確認する。
  Phaser 3 の API が利用可能であると仮定しない。
- ゲームの画像と音楽は `public/assets/` に配置し、アセット URL と Vite の base は
  サブパス配布に対応する相対パスを維持する。
- Tauri は共通の Web ビルドを包む構成を維持する。ネイティブ API や権限を追加する場合は、
  必要性と対象権限を計画とレビューに記録する。
- `Cargo.toml` の依存変更では `src-tauri/Cargo.lock` も更新し、`--locked` ビルドを維持する。
  Rust・デスクトップの検証は Web 側の CI で代替せず、対応環境または手動 Release で確認する。
- ロゴ変更時はデスクトップアイコンと Web アイコンを同じデザインから再生成する。
  Windows のユーザー単位 NSIS とシステム全体 MSI の配布用途を維持する。
- `main` への変更は PR を経由し、履歴は squash または rebase による線形履歴にする。
  公開済み `v*` タグを移動・削除せず、修正は新しいバージョンとして出す。
- バージョン変更をマージしてから、その `main` のコミットに
  `v` + `package.json` の version と一致するタグを付ける。
  正式リリースは全対象 OS のバンドル成功後に公開し、その後 Pages を更新する。
  ハイフン付きのプレリリースでは Pages を自動更新しない。
  Pages の手動再配布は Release ワークフローの既存タグ指定を使う。

## 開発手順と判断基準

1. 仕様書に、日本語でプレイヤーの課題、期待する結果、受け入れ条件、対象外を記述する。
   状態・セーブ互換性・操作の一貫性への影響を明確にする。
2. 計画書に、変更する責務、候補の比較、採用理由、検証方法を記述する。
   各基本原則への適合を確認し、性能への影響がある場合は測定条件と合格基準も定義する。
3. タスクを依存順に分割し、実装と必要な検証の完了条件を記述する。
   受け入れ条件がどのタスク・検証で満たされるかを追跡可能にする。
4. 変更範囲に応じて `pnpm lint`、`pnpm typecheck`、`pnpm test` を実行する。
   配布物に影響する変更では `pnpm build` を実行し、必要な実機・画面検証も行う。
   文書のみの変更では内容・整合性確認を行う。
5. レビューでは基本原則、受け入れ条件、検証結果、互換性、性能の順に適合を確認し、
   残る制約と例外を日本語で記録する。必須 CI の成功後にマージする。

技術判断では、進行状態と計算の正しさを必須条件とし、その条件を満たす案の中で
ユーザー体験の一貫性、検証可能性、性能基準、保守負担を比較する。
既存の責務と部品で要求を満たせる場合は、それを採用する。
新規依存や複雑な抽象化を採用する場合は、既存構成では満たせない要求と検証可能な利点を示す。
原則と衝突する案を、実装の都合だけで採用してはならない。

## ガバナンス

本憲章は仕様・計画・タスク・レビューと技術判断の共通基準とする。
日常のコマンドや Phaser 固有の注意事項は `AGENTS.md` を参照し、
本憲章と不整合がある場合は計画・レビューで明示して解消する。

改定は PR で行い、変更理由、影響する原則、既存仕様・実装への影響、
必要な移行作業を日本語で提示し、メンテナーがレビューして採用する。
例外は対象範囲、理由、代替の検証・対策、解消条件を計画または PR に記録し、
メンテナーの承認を得る。必須 CI やリポジトリ保護規則を例外で迂回してはならない。

憲章のバージョンはゲームのバージョンとは独立したセマンティックバージョニングに従う。
互換性のない原則の削除・再定義は MAJOR、新しい原則や実質的な指針の追加・拡張は MINOR、
意味を変えない明確化・表記修正は PATCH を上げる。
制定日は初回採用日を維持し、最終改定日は内容変更時に更新する。
各機能の計画とマージ前レビューで憲章への適合を確認する。
冒頭の同期影響レポートはレビュー用の一時情報であり、コミット前に削除する。
