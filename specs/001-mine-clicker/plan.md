# 実装計画: Mine Clicker — 砂漠の採掘と自動化

**ブランチ**: `chore/spec-kit` | **日付**: 2026-09-28 | **仕様**: [spec.md](spec.md)

**入力**: `specs/001-mine-clicker/spec.md`。Phaser + Vite + TypeScript を使用する。

Spec Kit の機能識別名は `001-mine-clicker`。セットアップの BRANCH 値は機能識別名を返すが、実際の Git ブランチは `chore/spec-kit` である。この計画作成ではブランチを変更しない。

## 概要

既存 Dust Baron の採掘・購入・強化・達成・演出を利用し、全面的な作り直しは行わない。
主な差分は通貨表示の `Credits` 統一、実経過時間による通常収入、保存の項目別復旧、保存先ごとの単一セッションである。
純粋な経済処理と Phaser の表示・入力を分離し、既存保存キーと State のフィールド名を保持する。

## 技術的背景

**言語・バージョン**: TypeScript 7.0.2、ES2022、厳格型検査、erasableSyntaxOnly、明示的な `.ts` import。Node 26.10.0 を調査環境で確認。

**主要依存**: ロックファイル上の Phaser 4.2.1、Vite 8.3.0、Biome 2.5.14、Tauri 2。pnpm 12.5.1。ゲーム実行時の新しい外部ライブラリは追加しない。

**保存**: localStorage の `dust-baron-save-v1`、JSON の既存 State。ライブ状態は `run.state`。プレイ権は Web Locks の排他ロックで管理し、保存データには混ぜない。

**検証**: Node 組み込み node:test を維持。実ブラウザのロック・画面再入場・保存を検証するため、実装段階で `@playwright/test` を開発依存として追加し、採用した安定版を pnpm-lock.yaml に固定する。既存 `pnpm test` と `pnpm build` の意味は維持し、ブラウザ検証は別の `pnpm test:e2e` とする。

**対象環境**: HTTPS または localhost の Web Locks 対応ブラウザ、Windows/macOS/Linux の対応 WebView。Desktop の API 実動作は対象 OS で確認し、非対応環境を対応済みとして出荷しない。

**種類・規模**: 単一クライアントの Web/デスクトップゲーム。自動生産6種類、採掘強化1種類、達成目標1種類、保存先ごとに書き込み主体1画面。サーバー・認証・クラウド同期は追加しない。

**性能目標**: SC-007 の平均55 FPS以上（目標60）、入力反応の95%以上が100 ms以内。毎フレームの保存・無変更時の行再描画を禁止。背景経過の精算はフレーム数に比例する反復ではなく定数個の区間計算にする。

**制約**: 1280×720 / Scale.FIT、対象テクスチャのみ NEAREST、相対アセットURL、Tauri core:default を維持する。非表示中の100%収入と閉じた後の50%収入を別経路にし、同じ時間を二重計上しない。

### 実装方針と依存順

1. 既存の経済・保存・UIと FR-001〜018 の対応を記録し、純粋関数の回帰検証を準備する。
2. 保存復旧を項目単位に厳密化し、既存JSONを受理する。小数の所有数・強化は切り捨てず不正項目として0にする。不正日時では離席加算しない。タイトルのCONTINUE判定はtotalだけでなく正常な所有物・強化・達成も考慮し、復旧した進行を新規開始で消さない。
3. `production.ts` で経済の時刻カーソルを進める。表示deltaは演出だけに使う。購入・採掘・保存・非表示・復帰の前に未精算時間を精算する。
4. `session.ts` で起動時に排他ロックを取得し、所有者だけ Phaser.Game を起動する。後の画面は英語DOM案内を表示する。取得前にはタイトルの保存読み込みや NEW RUN も実行しない。
5. シーンの表示を Credits に統一し、通常収入・達成・設定・一時効果の表示を契約に合わせる。描画・音声・購入数量の既存ルールを保持する。
6. 自動検証と実画面・性能・初見参加者検証を行い、結果と未実施項目を日本語で記録する。

既存価格のまとめ買いは `ceil(sum(baseCost × 1.15^(owned+k)))` の合計切り上げを維持する。単品ごとに切り上げて合算する方式へ変更しない。MAXは同じ式で次の1個が買えないことを検証する。

### 時間・一時効果・終了の設計

経済用の `accountedAtMs` を run に置き、現在時刻までの区間を一度だけ精算する。
連続精算は同じ時刻で収入0となり、購入前に精算するため購入後の能力を過去へ遡及しない。
負の時間差は収入0とし、時刻カーソルを後退させない。

砂嵐とフレンジーの有効期限を実時刻で扱う。既に有効な砂嵐は未精算区間との重なりだけ2倍とし、期限後は通常速度に戻す。
非表示中の未発生イベントを大量に再生せず、新しい出現は復帰後のスケジュールで行う。キャッシュの既存寿命も復帰時に失効を確認する。
タイトル・達成画面へ移るときに精算して保存し、ライブrunがある画面滞在分も復帰時に通常収入として精算する。

定期保存と購入保存に加え、非表示・pagehideで可能な範囲の精算・保存を行う。pagehideで所有状態を終了し、bfcacheから復帰したときはロックを取り直し保存を再読込する。強制終了では終了イベントを保証できないため最後の成功保存を復旧基準とする。
ゲーム破棄・HMRでは旧ゲームの停止を完了してからロックを解放する。DOM・game.events購読を解除し、再起動で購読を積み重ねない。

### 測定と受け入れの条件

- 基準端末: 調査ホストの AMD RYZEN AI MAX+ 395、Linux WSL2 x86_64。測定は同端末のWSLg上のheaded Chromium、60Hz、DPR1、1280×720、CPU/通信スロットリングなしで実施する。
- ブラウザは実装時に固定したPlaywrightの同梱Chromiumを使用する。基準測定時にOS・ブラウザの完全なバージョン・GPUレンダラーを記録し、比較測定も同じものに固定する。CIのheadless計測を実機FPSの代替にしない。
- ウォームアップ10秒後に60秒測定、3回実施。通常プレイ条件は6種類各25個、採掘強化3、2クリック/秒、10秒ごとに購入モード切替、一時効果なし。別途砂嵐・粒子を有効にした負荷条件でも同じ合格基準を確認する。
- 入力反応はpointer/keyboardイベント時刻から残高変更が反映される描画フレームまでを計測。95パーセンタイル100 ms以内、各試行の平均FPS55以上。基準コミットと実装後コミットを同条件で比較する。
- 再入場を10回実施し、同一ハンドラーの重複、音楽の重複、canvasの増加を0件とする。メモリは各試行後の落ち着いた状態を記録し、残存購読・オブジェクトが回数に比例して増える場合は修正する。
- SC-009は初見5人へ英語UIだけを提示し、助言せず2分計測する。4人以上が最初の雇用と自動収入の説明に成功すること。自動テストで参加者検証の成功を代替しない。
- ブラウザ排他検証は同一BrowserContextの複数pageで行う。別Contextは保存先が別なので対照検証に使う。最小化は実機で確認する。
- Desktopは対応する実機・Release成果物で基本操作、Web Locks、保存復旧を確認する。現WSLに不足するWebViewシステム依存による未実施は明記する。

## 複雑性の管理

憲章違反はない。追加するPlaywrightはnode:testだけでは証明できない実ブラウザ排他・保存・シーン再入場の回帰を防ぐ目的に限定する。
