# 調査結果: Mine Clicker

**日付**: 2026-09-28
**対象**: [仕様](spec.md)、[憲章](../../.specify/memory/constitution.md)

## 1. 既存構成を維持する

**決定**: Phaser 4.2.1、Vite 8.3.0、TypeScript 7.0.2 のロック済み構成を使用する。基盤の更新や別アプリ化を行わない。

**理由**: `src/economy.ts` にクリック量、価格、生産倍率、購入、達成、離席収入が既に分離され、既存 `economy.test.ts` がある。`main.ts` は固定1280×720とFIT、Viteは相対baseを採用している。

**比較した案**: 新規ゲームの生成、別UIフレームワーク、経済処理のシーン内再実装。既存資産・保存互換性を失う負担に見合う要求がないため不採用。

**根拠**: `package.json`、`pnpm-lock.yaml`、`src/main.ts`、`src/config.ts`、`src/economy.ts`、`vite.config.ts`。

## 2. 生産用の実経過時間を描画時間から分離する

**決定**: run単位の時刻カーソルを使い、未計上区間をeconomy.tsの純粋関数で精算する。通常の実時刻区間を100%、閉じて再開する区間のみ50%・最大2時間とする。生産・一時倍率もゲームルールであるため、憲章IIに従ってeconomy.tsへ集約し、production.tsは追加しない。production.test.tsはeconomy.tsの時間計算を検証する独立したテストファイルとする。

**実装時の確認**: WSLgのブラウザで20.2秒の単調経過中に実日時が17.7秒しか進まず、Date.nowを生産に使うと収入不足になることを再現した。ライブ時計と一時効果期限はperformance.now由来の単調経過に統一し、保存日時・離席には実日時を維持する。

**理由**: 現在 `Game.update()` はdeltaを250msに制限し、PhaserのHIDDEN時はループが停止する。現コードにVISIBLE補償がなく、長い非表示時間の生産が欠落する。Phaserの描画ループを強制的に動かしても、ブラウザによる停止・遅延は解決しない。

**比較した案**: deltaの制限を単に外す、タイマーを高頻度で常時動かす、VISIBLEでofflineGainを使う。演出の暴走・停止中の不足・50%への誤変換・二重計上が生じるため不採用。

**一時効果**: 実時刻の終了境界で区間を分割し、既に有効な砂嵐の残り時間だけ倍率を適用する。非表示中に新規イベントを遡って大量発火しない。初期の未発生イベント予定は復帰後に再開する。

**根拠**: `src/scenes/Game.ts`、`node_modules/phaser/src/core/Game.js` の onHidden/onVisible、`node_modules/phaser/src/core/TimeStep.js`。非表示・最小化はdocumentのvisibility状態で観測する。[HTMLのページ可視性仕様](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility)を参照。

## 3. Web Locksで最初の1画面に限定する

**決定**: `navigator.locks.request` に保存キー由来のロック名、`mode: 'exclusive'`、`ifAvailable: true` を渡す。ownedまたはAPI非対応・取得例外のephemeral判定後にPhaser.Gameを起動する。競合で取得できない後続画面は待機列に入れず、英語案内を表示して停止する。

**理由**: ロックは同じ保存領域を共有する画面の排他制御に使える。保持Promiseが終了するまで所有し、ページ終了時も解放されるため、背景タイマーの遅延による権限の横取りを避けられる。[Web Locks公式仕様](https://w3c.github.io/web-locks/#api-lockmanager-request)、[ロックの終了](https://w3c.github.io/web-locks/#termination-of-locks)。

**実装上の注意**: `ifAvailable` と `signal` は併用しない。request全体は解放まで未完了なので、起動への取得結果通知と保持Promiseを分ける。`steal` は使用しない。HMRの旧ゲーム終了、DOM/game購読解除の完了後に解放する。非表示だけでは解放しない。

**比較した案**: localStorageの期限付きheartbeat、BroadcastChannelだけの選挙、サーバー同期。期限切れは最小化中の所有者を奪う可能性があり、単純なread/writeは同時取得を防げない。サーバーは対象範囲を超える。

**未対応時の決定**: ユーザー回答に従い、API非対応・取得例外ではephemeralとして新規の一時プレイを許可する。英語で保存なしを常時案内し、共有保存の読込・書込・削除と離席収入を禁止する。競合blockedは一時プレイへ切り替えない。一時プレイは再読み込みまで同じメモリ内runを使い、途中でownedに昇格させない。再読み込みでは一時進行を破棄して取得を再判定する。ロック取得成功後のlocalStorage失敗では所有者の同じrunとロックを保持して継続する。既存保存を排他なしで使うフォールバックは置かない。

**確認事項**: DesktopのWebViewも実装時に機能検出と実機検証を行う。対象環境の検証が失敗した場合は対応済みと報告しない。API非対応と競合中を同じ通知にしない。

## 4. 保存形式は維持して項目別に復旧する

**決定**: `State.scrap` と保存キーを維持し、UIだけCreditsと表記する。復旧関数ではオブジェクト構造・数値・整数・真偽値を検証し、不正な項目だけ初期値へ戻す。生産量は復旧された所有数から求める。

**理由**: 現在のdeserializeは不正値を0にするが、小数の所有数・強化を切り捨てるほか、進行オブジェクトでない値を受理しうる。不正日時の0を離席計算へ渡すと過大な収入につながる。

**比較した案**: すべて初期化、新しい通貨フィールドと保存キーへ移行。正常な進行を残す回答Aと既存データ保護に反するため不採用。

**時刻**: 純粋な解析段階は日時無効を0で示し、起動段階で現在時刻を基準にする。未来日時は離席0。不正日時では加算しない。正常な離席加算後は直ちに保存し、シーン遷移では再読込しない。

**保存失敗**: 成功保存日時とメモリ内の時刻カーソルを混同しない。書き込み失敗でもライブrunは維持する。終了イベントが実行されない強制終了や保存不能では、未保存の進行を保証できない。再読込時は最後の成功保存から復旧する。

**根拠**: `src/storage.ts`、`src/economy.ts` の State / deserialize / offlineGain、仕様の確認事項。

## 5. 経済式と表示を一致させる

**決定**: 既存のまとめ買いは未丸め価格の幾何級数を合計して一度だけ切り上げる。MAXの表示と購入は同じgenCostを使う。単品・10個・MAXの合計費用を同一の丸め方法で表示する。

**理由**: 現在の `genCost()` と経済テストが合計切り上げ方式である。単品ごとの切り上げへ変えるとバランスが変わる。Creditsの文言だけを変え、資源としてのスクラップを描く説明は残せる。

**比較した案**: 通貨ごとの残高を追加、採掘後に売却、まとめ買い式の変更。要求に不要な手間と保存移行が増えるため不採用。

## 6. 検証は純粋ロジックと実ブラウザを分担する

**決定**: Nodeの経済テストに復旧・時刻境界を追加し、Playwrightで同一保存先の複数画面とシーン再入場を検証する。最小化、FPS、初見参加者は実画面で確認する。

**理由**: node:testでは実際のWeb LocksやPhaser入力を証明できない。Playwrightの別BrowserContextは保存先が分離されるため、競合検証は同じContext内の複数pageで行う。[Playwright公式の隔離モデル](https://playwright.dev/docs/browser-contexts)、[BrowserContext API](https://playwright.dev/docs/api/class-browsercontext#browser-context-new-page)。

**比較した案**: すべてをNodeのモックだけで確認、全項目を毎回手動確認。APIや入力の実統合を見落とす、または再現コストが高いため、重要な回帰だけ自動化する。

## 調査完了の判定

技術選定・時間計算・排他・復旧・検証方法の未決定事項はない。実装後の対応環境検証、性能測定、参加者検証は合格判定の作業であり、未解決の設計選択ではない。
