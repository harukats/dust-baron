# 検証ガイド: Mine Clicker

このガイドは合格確認用である。実装・自動テスト・実画面・性能・参加者の検証結果は [validation.md](validation.md) と [performance.md](performance.md) に記録し、未実施を合格と扱わない。

## 前提と準備

- Node 22.18以上（比較環境では26.10.0）、packageManagerで指定したpnpm、Web Locks対応のブラウザを用意する。
- このリポジトリのルートでコマンドを実行する。実ユーザーの保存を使わず、専用プロファイルを用意する。
- 排他検証では同じプロファイル・同じoriginのタブを使う。別プロファイルは保存先が異なる対照条件である。
- DesktopにはRustと対象OSのWebView依存が必要。現WSLでは不足しているためDesktop未検証を成功扱いしない。

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm dev
```

ゲームを `http://localhost:8080` で開く。正式なPagesサブパスでも相対アセットが読めることを配布前に確認する。
実装済みE2Eのコマンドは以下とする。

```sh
pnpm exec playwright install chromium
pnpm test:e2e
```

Playwrightを開発依存に追加した実装コミットのロックファイルを用いる。ブラウザ配布物の取得が必要な初回だけインストールする。

## 1. 手動採掘から最初の自動化

1. 専用プロファイルで新規開始する。英語の開始案内、Credits 0、採掘量1、生産量0を確認する。
2. 1秒ごとに鉱床をクリックして15以上を稼ぐ。30秒以内にSCAVENGERを雇い、費用15と毎秒0.5を確認する。
3. 20秒操作せず、10±0.5を得る。Spaceでもクリックと同じ1操作分を得る。装飾クリックでは収入を得ない。
4. 単品・10個・MAXを切り替え、表示額と実際の支出、全額不足時の無変更を確認する。SCAVENGER所有0・残高305ではx10とMAXが10個・305、残高304のx10は無変更であることも確認する。

価格・倍率・強化の正確な値は [仕様](spec.md) と [UI契約](contracts/ui.md) を参照する。

## 2. 保存と離席

1. 人員・装置・強化を持つ進行を5秒以上待って保存する。購入直後にも保存が更新されることを確認する。
2. 同じ画面を再読み込みし、正常な所有物・強化・達成を確認する。10回繰り返す。
3. 通常生産毎秒2、一時効果なしの保存から60秒閉じて再開し、離席収入60を一度だけ得る。
4. 加算直後に再読み込みして同じ離席収入を再受領しない。シーン移動でも再加算しない。
5. 29秒、30秒、7200秒、7201秒、未来日時を純粋関数の時刻固定テストで確認する。2時間の実待機は不要。

保存構造・正規化・失敗時の制約は [保存契約](contracts/persistence-session.md) を参照する。

## 3. 非表示・最小化

1. 通常毎秒2、一時効果なしの状態を用意し、開始残高と時刻を記録する。
2. 別タブへ移動して60秒待ち、復帰後に120±2を得る。5回繰り返す。
3. ウィンドウを最小化して同じ検証を5回実施する。OSの通常操作で行い、単なる合成visibilityイベントだけで合格としない。
4. 同じ期間の50%離席収入が追加されないことを確認する。
5. 非表示のまま通常の手順で閉じて再開し、閉じる前までの通常収入と閉じた後の離席収入を別々に確認する。
6. 砂嵐の開始直後に隠して期限後に戻り、期限内だけ2倍となる。フレンジー・キャッシュも期限を超えて継続しない。

## 4. 壊れた保存と保存失敗

専用プロファイルでだけ保存fixtureを作成する。正常な旧Stateに対し、残高、各種類の所有数、pick、won、lastSaveを一項目ずつ不正または欠落にして再開する。
不正値には負数、文字列、null、小数整数を含める。全体には壊れたJSON、配列、null、進行項目のないオブジェクトを使う。

- 正常項目を保持し、不正な項目だけ初期値へ戻る。
- 不正日時では離席収入0、未来日時でも負の収入0。
- 各種類の所有数の復旧が他の種類を消さない。
- localStorageの読込・書込が例外になる状況でも、ロック取得済み画面は現在の採掘・購入を続けられる。
- 正常な既存保存をCreditsへの変更後も同額で復元する。

合格条件はSC-011。保存日時は無限の過去として扱わない。

## 5. 同時プレイと終了

1. 最初のタブAで開始してから、同じ保存先のタブBを開く。
2. Bには `GAME ALREADY OPEN` と再開案内が英語で表示される。Bの入力・待機・NEW RUN相当の操作で進行や保存が変わらない。
3. Aを非表示・最小化してもBがプレイ権を奪わない。Aの保存と生産は維持される。
4. Aを閉じてBを再読み込みし、保存された進行から再開できる。別タブ・別ウィンドウで各5回行う。
5. 同時起動でもownedは1画面だけとなる。別BrowserContextでは独立してプレイできる。
6. HMR後にcanvasとプレイ権が重複せず、履歴復帰ではロックを取り直す。
7. Web Locks非対応と取得例外をそれぞれ再現し、`TEMPORARY PLAY — NOT SAVED` と終了時に進行が失われる説明を常時表示する。一時プレイで採掘・雇用・自動生産・強化・シーン移動・非表示復帰が継続でき、共有保存の読込/書込/削除と離席収入が0件であることを確認する。
8. 一時プレイのNEW RUNがメモリ内だけを初期化することを確認する。再読み込みで一時進行を破棄し、取得成功時は既存保存だけから再開する。途中で共有保存へ昇格・合算しないこと、競合結果では一時プレイを開始しないことを確認する（SC-013）。

E2Eでは同じBrowserContextから複数pageを作り、Bを別Contextへ分離してしまわない。

## 6. 全UI・画面再入場・音声

開始、通常プレイ、ショップの購入可否、強化、砂嵐、キャッシュ、フレンジー、離席、達成、同時プレイ制限、環境案内の文言を一覧で確認する。
非英語のUI文言0件、通貨表記はCredits、購入数量と費用が一致すること。

1280×720と960×540で採掘・購入・ミュートを完了する。SOUND/MがBGMと効果音の両方へ反映される。
Title → Game → Victory → Gameの再入場を10回行い、1入力が複数回処理されず、進行とミュート状態が保持され、BGMが重複しないこと。

## 7. 性能・初見参加者・Desktop

[計画の測定条件](plan.md)で基準コミットと実装後を各3回計測する。OS・ブラウザ完全版・GPU・DPR・viewport・負荷・ウォームアップ・測定時間を同じにし、平均FPS55以上、入力反応p95が100ms以内を確認する。
headlessの結果で実画面のFPSを代替しない。未実施・測定不能な条件は理由を記録する。

初見5人へ外部説明なしにゲームを提示し、2分以内の最初の雇用と自動収入の説明が4人以上成功することを確認する。
Desktopは対応実機で基本操作、保存、排他機能の検出を確認する。Rust側を変更する場合はCargo.lock更新とReleaseの--lockedビルドも必要。

## 結果の記録

仕様のSC-001〜013について、環境、手順、期待値、実測値、合否、未実施理由を日本語で記録する。
Node・ブラウザテストの成功、実機測定、参加者検証を区別する。失敗を仕様変更で隠さず、解消または憲章に従った例外のレビューを行う。

## 実装済みの検証コマンド

Viteを起動してから `pnpm test:performance` を実行すると、headed Chromiumの計測値をtest-results/performance.jsonへ保存する。背景の実タブ・最小化検証は `pnpm exec node tests/e2e/runtime-check.ts` で行う。実機でvisibilityが切り替わらない場合は合格にせず、環境を変えて再検証する。

別タブ・別ウィンドウの排他検証は `pnpm exec node tests/e2e/window-check.ts`、全UI状態の画面記録は `pnpm exec node tests/e2e/ui-check.ts`、GC後の再入場メモリ記録は `pnpm exec node tests/e2e/memory-check.ts` で実行する。FPS測定中は他のブラウザ検証を実行しない。短時間のGC後ヒープ記録は、長時間動作やGPUメモリの保証を代替しない。
