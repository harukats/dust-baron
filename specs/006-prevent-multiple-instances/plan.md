# 実装計画: デスクトップ版の多重起動防止

**ブランチ**: 仕様選択名 `006-prevent-multiple-instances`（実装ブランチも `006-prevent-multiple-instances`） | **日付**: 2026-10-15 | **仕様**: [spec.md](spec.md)

## 概要

WebViewを開始する前にOSの排他ファイルロックを取得し、保持できたプロセスだけゲームを開始する。追加起動は既存プロセスへ表示要求を送り終了する。標準ライブラリのロックとローカル通信を小さなRustモジュールへ閉じ込める。公式単一起動プラグインだけでは同時起動の厳密な排他を保証できないため採用しない。根拠と代替案は[research.md](research.md)を参照。

## 技術的な前提

- **言語・バージョン**: Rust 2021 edition。`File::try_lock`を使うため `rust-version` を1.77.2から最低1.90へ上げる。ローカルはrustc 1.99.0、Releaseはstable。既存Cargo.lockのTauri 2.12.1もRust 1.90を要求するため、この最低値に合わせる。TypeScript 7 / Phaser 4 / Vite 8は既存のまま。
- **依存**: TauriはCargo.tomlで2.11.6以上の2系を指定し、既存Cargo.lockでは2.12.1。ユーザー別ディレクトリ解決の `dirs` と通知用乱数の `getrandom` を直接依存へ追加する。既存Cargo.lockのdirs 7.0.0 / getrandom 0.3.4を直接依存として使用する。新たなプラグインやJS APIは追加しない。
- **保存**: ユーザー別ローカルデータディレクトリ / `io.github.harukats.dustbaron` / `instance.lock` と `instance.endpoint`。ゲームのセーブとは別。ロックファイルは空で、削除・置換しない。
- **検証**: Rustの実プロセスによる競合・終了・通信試験、対象OSの実WebViewによる受け入れ試験、既存Webチェック。
- **対象**: Windows / macOS / Linuxの既存配布形式。Linuxはローカルファイルシステムを使う通常のデスクトップ環境。共有ネットワークファイルシステムは保証対象にしない。
- **性能**: ゲームのフレーム処理には追加処理なし。追加起動の通知待ちは総計2秒以内、通常のウィンドウ復元は要求から2秒以内を検証目標とする。起動中の読み込み速度を保証する数値ではない。
- **制約**: 排他不能・保存先解決不能ではゲームを開始せずエラー終了する。通知不能でも追加起動をゲームへ昇格しない。外部ネットワークやDBusに依存しない。
- **規模**: 所有者1プロセス、待受スレッド1つ、保留の表示要求1つ。画面やゲーム状態は追加しない。

## フェーズ1: 設計

1. `generate_context!()` の識別子とユーザー別ローカルデータパスから共通の保存先を決める。実行ファイルの場所・PID・バージョンをロック名に含めない。
2. 空の `instance.lock` を非切り詰めで開き `try_lock`。所有者のみ通知待受を準備してBuilderを開始する。競合は表示通知を試みて終了、それ以外のロックエラーは診断して終了する。
3. 所有者は `127.0.0.1:0` で待受し、32バイトの起動ごとの乱数を含むendpoint情報を公開する。通知は表示要求のみ。詳細は[契約](contracts/desktop-instance.md)。
4. 所有者の起動直後に届いた通知は1つにまとめて保持し、mainウィンドウ準備後に処理する。Tauriのメインスレッドへ配送し、`show`、`unminimize`、`set_focus` を個別に試みる。消滅済みのウィンドウを新規作成しない。macOSではFinder・Dockからの再オープンを `RunEvent::Reopen` で受け取り、通知と同じ表示復元処理へ接続する。起動準備中は要求を集約し、終了中は処理しない。
5. ロック保持者はゲームが動く全期間保持する。終了時は停止通知、通知スレッドのjoin、endpoint削除、最後にロックを閉じる。待受は非ブロッキングとし、接続がない場合は終了通知を待つ。終了通知で待機を即座に解除し、接続処理には読み書き全体で200msの総期限を設ける。ゲームの更新ループには待機処理を追加しない。接続なし・要求途中・通知処理中の各状態で終了処理が1秒以内に完了することを検証する。異常終了の残存endpointは次の所有者が上書きする。
6. [quickstart.md](quickstart.md)で実装前後を比較し、`validation.md`へ実測結果を残す。現在の文書作成ではテストやRelease実行は行わない。

## 複雑さの評価

公式プラグインの競合経路をアプリ側で補強しつつ通知機構を二重管理する案より、ロックと限定された表示通知を1モジュールで所有する。汎用IPC基盤、コマンド実行、独自ロックファイル存在判定は導入しない。小規模でも排他と通信のテストは必須とする。
